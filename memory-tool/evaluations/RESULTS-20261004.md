# Memory selection comparison, 2026-10-04

The revised policy supplied enough evidence to answer this fixed synthetic task
without retrieval calls at all three budgets. This supports a 24k initial default
with up to 8k recent history; it does not establish an optimal budget or general
recall improvement. At 24k and 64k, baseline answers were also correct in meaning.

## Protocol and provenance

The [protocol](selection_protocol.json) fixed 12 questions, exact expected answers,
seed 9371, a common 8,000-token recent allowance, and 12,000 / 24,000 / 64,000 total
packet ceilings before implementing selection. The [corpus](selection_corpus.py)
contains old and corrected decisions, stale status, unresolved claims, repeated
tool output, a long diagnostic tail, other-session/project distractors and pinned
notes. It contains no private conversation text. Questions and expected answers
were not changed after results arrived.

Baseline source was personal-tools commit `de61890eae33a28ae6990f0f99960fb7fd032849`
(memory-tool 0.2.0). Both versions used an authenticated `gpt-5.6-luna` reader with
the same instructions, questions and at most 12 executed search/zoom calls. The
seed fixes the corpus, not model generation. Retrieval beyond that limit returned
a budget error, so attempted calls can exceed executed calls. Readers were
ephemeral and had no shell, apps, inherited hooks or workspace access.

Protocol SHA256: `68cbace5f61077a49f9073d29b308449644f0d5f234e0763812d5fcbbe27af8f`.
Corpus SHA256: `f6b62a01fd60a05a9ccb17c3a986ecd60d2ebcb03a52c29c7c28bae5622a194d`.

Every version/budget found all eight designated raw sources in the local candidate

The strict grader has two documented wording issues. The restart question asks
whether another restart is required but expects `VERIFIED`; release readers
answered `NO`, consistent with the source. They also returned a longer correct
phrase for the pending duplicate-suppression task. Manual inspection found all
12 release answers correct in meaning, but the frozen strict score remains
**10/12**, not 12/12. Baseline 24k/64k missed only the pending-task exact wording;
baseline 12k additionally missed the corrected cap and long-output tail. This
manual interpretation is post-hoc and is not a separate blinded metric.

`selective-*` preserves the first implementation's real failure: it omitted the
older compaction-threshold decision when recent topic vocabulary changed. A bounded
reserve of older direct user turns fixed that regression. `final-*` preserves the
next development iteration; `release-*` records the scoped release selection.
These are development iterations, not independent replicate trials. Implementation
hashes were added to the runner for release trials; earlier JSON files lack them.
The implementation was iterated against this fixture, so it is not held out.

The final whitespace/preference/CLI/transport fixes did not change any of the three saved
release packets. [verification.json](results-20261004/verification.json) records
the final source hash and byte-identical packet checks. No model rerun was needed
for identical packet inputs; the release trials retain their original source hash.

## Real archive audit

A SQLite-consistent local snapshot was compared separately. Private archive files,
packed text and retrieval passages are excluded from the repository. In that
snapshot a pre-release scoped audit omitted 572 other-session events, nine
other-session notes, 14 off-topic notes, two expired notes and six expired status
events. It selected seven notes. Packet tokens were:

| Ceiling | Baseline | Scoped selection |
|---|---:|---:|
| 12,000 | 11,952 | 11,951 |
| 24,000 | 19,043 | 19,673 |
| 64,000 | 21,277 | 19,673 |

This is a different corpus from the synthetic table. Selection need not always
produce a smaller packet. The 12k option truncates more of the real snapshot;
24k gives headroom while 64k added no material here. That is the practical reason
for choosing 24k, rather than claiming a statistically established optimum.

For one known question about retaining working context for cache reuse, the two
direct assistant explanations moved to positions one and two. The query's tool
documents were changed versions, not exact duplicates, so duplicate removal was
**not** responsible for this improvement; the explicit source-role presentation
policy was. Initial Jev requests were three in both versions, with 5,296 versus
5,456 reported input tokens. Later checks reused all three cached batches. This
does not demonstrate fewer paid requests or fair latency improvement. Exact-copy
grouping is covered by synthetic regressions; this single real question was used
during development and is not independent validation.

## Limits and reproduction

Model input totals sum internal requests, including retrieval rounds. A total
above 200k does not mean any single request exceeded the context target. Shared
provider cache, sequential ordering, short answers and one run per version/budget
confound latency and billing comparisons. No dollar-savings claim is made. The
archive's immutable raw source and exact zoom remain available, but lexical
shortlists, literal previews, status regexes and topic selection can miss facts.
Independent real-user evaluation remains tracked separately as `bff-7uw`.

From memory-tool, with Codex authenticated (each `--out` must be a new directory):

```powershell
uv sync --group dev
uv run pytest -q -p no:cacheprovider
uv run ruff check src tests scripts evaluations
uv run python evaluations/run_selection.py --source src --budget 24000 --out private/reproduction-24000 --live
uv run python scripts/live_native_hooks.py
uv run python scripts/live_native_mcp.py --local
```

Repeat the evaluation command with 12000 and 64000 and distinct output directories.
For baseline reproduction use a separate checkout of the recorded commit as
`--source`; do not overwrite a running installation. Without `--live`, the runner
builds the packet and measures local source candidates only. Live probes use the
configured Codex account and native hook probes require normal trusted hooks.
